# 3.0.0 核心包重构报告

> **重构目标**：消除早期 MVC 脚手架遗留的 `domain` 大杂烩，让 DDD、CQRS、技术契约、技术事件在命名上直接体现架构意图
> **重构策略**：硬切换 + 全工作区引用同步迁移，不保留新的旧包兼容壳

---

## 一、问题诊断

### 1.1 旧包结构（4 包关系混乱）

```
io.ddd4j.core/
├── contract/        ← 老契约层（Model/Query/R/BaseRepository/DomainEvent/MQEvent）
│                       ← 同时混入 R/IR/ServiceException 这些响应模型和异常
│
├── domain/          ← 新增"轻量 DDD"（AggregateRoot/Entity/ValueObject/DomainModel）
│                       ← 与 ddd 包功能重复
│
├── ddd/             ← fuinorg 包装层（DddAggregateRoot/DddCommandExecutor/DddView/JpaView）
│                       ← 与 cqrs 包功能重复
│
└── cqrs/            ← 框架无关投影抽象（ProjectionView/ViewManager/EventChunk）
                        ← 命名与 ddd.query 完全重叠
```

### 1.2 10 大关系混乱点

| # | 概念 | 出现位置 | 问题 |
|---|------|---------|------|
| 1 | **聚合根基类** | `contract/Model` / `domain/AggregateRoot` / `ddd/aggregate/DddAggregateRoot` | 3 条平行轨道，业务方不知道该继承哪个 |
| 2 | **领域事件** | `contract/DomainEvent` / `contract/MQEvent` / `ddd/event/DddDomainEvent` / `cqrs/projection/TypedEvent` | 4 种事件，语义重叠 |
| 3 | **仓储接口** | `contract/BaseRepository` / `contract/Repository` / `domain/DomainRepository` | 3 个仓储接口 |
| 4 | **视图抽象** | `ddd/query/DddView` / `ddd/query/DddJpaView` / `cqrs/projection/ProjectionView` | 两个体系各做一遍 |
| 5 | **`contract` 包名不准** | 含 Model/Query 通用契约 + R/IR/ServiceException 响应 | 让人误以为是"接口协议" |
| 6 | **`domain` 与 `ddd` 混淆** | 仅靠 `Ddd` 前缀区分 | 不够直观 |
| 7 | **`cqrs` 仅有一层 `projection`** | 实际混合 View 和事件分发两类抽象 | 职责分裂 |
| 8 | **`cqrs` 命名有歧义** | 应包含 Command/Query/Projection 三部分 | 但只放了投影 |
| 9 | **`cqrs.projection` 职责分裂** | View / TypedEvent / Dispatcher 混在一起 | 不内聚 |
| 10 | **`contract` 兼做"响应模型"** | R/IR/ResultCode 是 HTTP 响应 | 不属于 DDD 契约 |

## 三、合并决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 旧 `domain` 大包拆分 | `ddd/cqrs/api/enums/event` | 顶层命名直接表达架构关注点 |
| DDD 战术对象 | `ddd/model/repository/event` | 聚合、仓储、领域事件放在同一 DDD 命名空间 |
| CQRS 对象 | `cqrs/command/query/readmodel` | Command、Query、Read Model 明确分离 |
| `Page/R/IR/ResultCode` 放 `api/` | ✅ | 不是 DDD 战术元素，也不是领域契约 |
| Web/MQ 注解离开 core | `webmvc.annotation` / `mq.annotation` | 注解归属实际适配模块，避免 core contract 大杂烩 |
| 三条聚合根轨道 → 一条 `AggregateRoot` | ✅ | 业务方只看到一条 |
| 领域事件与 MQ 事件分离 | `ddd/event` + `event` | 避免业务事件与技术事件语义混用 |
| 兼容路径保留 | ❌ | 架构设计阶段直接硬切，避免继续传播旧命名 |

## 七、版本说明

- **3.0.0**：本变更落地版本
- **核心模块状态**：已硬切换（ddd4j-core）
- **下游模块状态**：ddd4j-data / ddd4j-mq / ddd4j-runtime / ddd4j-web 已同步包路径
- **建议**：
  - DDD 模型：直接采用 `io.ddd4j.core.ddd.*`
  - CQRS 对象：直接采用 `io.ddd4j.core.cqrs.*`
  - API 响应/分页：直接采用 `io.ddd4j.core.api.*`
  - MQ 监听注解：直接采用 `io.ddd4j.mq.annotation.*`
  - WebMVC Feign 注解：直接采用 `io.ddd4j.web.webmvc.annotation.*`
  - MQ 等技术事件：直接采用 `io.ddd4j.core.event.*`
