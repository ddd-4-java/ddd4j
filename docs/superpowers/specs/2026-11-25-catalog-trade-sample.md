# 28 个现有示例的商品交易业务

在 JDK 21 的七个框架中，以同一套商品交易用例替换默认、CQRS、Sa-Token 和 Shiro 入口中的旧订单业务。保留 28 个可运行模块及其启动类，COLA 的领域、应用、客户端契约与基础设施代码归入已有共享模块。

以 catalog-trade.sql 定义的四表为契约。应用启动时通过 MyBatis 执行原始 DDL，在专用 MySQL 库初始化四表。初始化失败时应用启动失败。重启后保留订单和成交快照。每个框架应通过实际 HTTP 验证建档、按规格与购买数量下单、读取快照、租户隔离和业务键冲突。共享仓储另验证商品建档事务回滚及目录改价后历史订单金额。该流程以不限量套餐为例，商品名称、价格和订单金额由服务端确定。

## 支付确认与重试

所有支付确认 HTTP 入口要求非空白的 `Idempotency-Key`。已获写权限的调用缺少该头时返回 400，订单仍待支付。同一租户对同一订单使用原键和金额重试，返回首次确认的快照，只发布一次支付确认事件。已确认订单以不同金额重试返回 409，原实付金额及支付时间保留。订单事务锁定现有订单行，使用四张业务表完成判定。认证入口在执行支付前依原有规则验证身份和写权限。

## CQRS 和原生鉴权模式

七个框架的 CQRS、Sa-Token、Shiro 入口都复用四表初始化和共享应用服务。CQRS 写入走框架命令总线，读侧按租户和订单号从成交快照构造可重建的独立视图。验收应观察写入后查不到、投影后查到、跨租户查不到。原生认证模式应验证未登录拒绝、只读账号拒绝写入、写账号完成交易，并使用原有会话和权限入口。

## DDD4J 基础契约

商品和订单继承 `AggregateRoot<Long>`，规格和订单明细实现 `Entity<Long>`，成交报价实现 `ValueObject`。商品审核和库存初始规则、成交快照、金额计算和交易初始状态由领域模型负责。应用只编排事务、领域操作与仓储。MyBatis PO 保持四表列映射。

商品交易应用使用 DDD4J 的泛型 `Repository`、`Command`、`CommandExecutor`、`Query`、`QueryHandler` 与总线。写命令只携带有类型的业务字段。CQRS 读模型通过 `ProjectionView` 从已提交交易重建，查询由 `QueryBus` 路由。现有 HTTP 入口和四表初始化继续使用同一套业务。

四表分别映射到 `GoodsSpu`、`GoodsSku`、`TradeOrder`、`TradeOrderItem`。HTTP 返回领域字段名，建档使用 `spuName` 和 `salePriceCent`，成交快照使用 `productNameSnapshot`、`skuNameSnapshot` 和 `unitPriceCent`。

## 旧订单入口收口

商品交易模式只注册四表业务路由。鉴权样例继续注册原生登录、退出和角色权限接口。验收检查商品建档、下单、查询及投影照常工作，并检查旧 `POST /orders` 和 `POST /api/orders` 在商品交易模式中返回 404。

## 历史订单退役

四张业务表也是本示例的全部持久化表。订单查询投影从已提交的交易快照重建。交易样例的状态变更使用四表已有的状态、金额和时间字段，并验证事务边界和租户隔离。移除旧订单服务和模型、内存订单仓储、PostgreSQL 订单装配与示例专用 Outbox。七个框架保留原有命令总线和鉴权。

## JDK 21 验收

28 个模块共 29 个 HTTP 入口逐个启动验收，Spring 的 WebMVC 和 WebFlux 分别验证。四表字段与原始 SQL 一致，验收覆盖建档、下单、支付金额校验与重复支付、履约、租户隔离以及旧入口退役。CQRS 入口另验证取消、投影前后查询和快照重建。原生鉴权回归覆盖未登录与权限拒绝、令牌失效以及请求上下文清理。

## COLA 边界整改

启动层组装 HTTP 适配器、应用服务和 MyBatis 事务。持久化构件仅依赖领域契约，把业务键冲突转换为业务异常，再由 HTTP 适配层映射 409。商品和订单使用具名创建与恢复入口，恢复时复制集合。CQRS 使用独立的订单读模型，同一租户和订单的快照读取与写入视图串行执行。显式投影仍可从四表重建。交易事件经各框架的 DDD4J 发布器在提交后分发。保持四表 DDL、端点、鉴权和命令总线，增加分层、并发、聚合不变量及事件回归。
